# 文档即地图（doc-as-map）

## 这条规则解决什么

**改一处、落一处**：同一个事实在代码、文档、记忆里各说各话，谁都不权威。
本规则把文档变成代码的地图：**先有地图，再改地形；每改一处，地图立刻更新并留痕。**

---

## 一、准备

若项目内不存在 `fixlog/`，先建 `<项目根>/fixlog/`。
该目录是本项目**唯一的工程文档与修复台账区**。

---

## 二、三份必备文档

### 1. `fixlog/ARCHITECTURE.md` —— 架构文档

必含：系统分层、模块职责与边界、模块间调用方向、数据流与状态流向、外部依赖及作用、启动与配置入口、
**模块依赖关系图**、**功能索引表**（功能 → 模块目录 → 关键文件 → 说明）。

> 验收判据：读者仅凭此文档即可定位任一功能所属模块。

### 2. `fixlog/API.md` —— 接口文档

按项目实际存在的接口类型分章：HTTP/RPC 接口、内部命令、工具方法、事件与回调。
每条含：名称与签名、入参（类型/必填/取值范围/默认值）、返回值结构、错误码及触发条件、调用方、实现位置（`文件:行号`）。

某类接口不存在时，明确写「本项目无此类接口」，**不留空章节**。

> 验收判据：读者能查到某接口的入参与错误码。

### 3. `fixlog/缺陷修复记录.md` —— 唯一修复台账

只增不改，按审核批次分节，互不覆盖。

```
批次索引表（批次 / 日期 / 来源 / 条目数 / 已修 / 不修 / 结转）
↓
## B-YYYYMMDD-NN · 批次名
### 本批清单（核对基线）   ← 编号后的审核问题清单，必须在动代码之前写
### 本批记录               ← 逐条：编号/来源/问题/根因/改动文件与函数/验证/日期/状态
## 待跟踪（跨批次结转池）
```

每条必含：编号、发现来源、问题描述、根因、修改涉及的文件与函数、验证方式、日期、
状态（待修 / 已修 / 不修及理由）。

---

## 三、修复范围与顺序

1. **先建或更新架构文档与接口文档，再动代码。**
2. 按本次审核清单**逐条修**，每完成一项**立即**登记状态，不许全部改完再一次性补记。
3. 确有不修的，写明理由并标「不修」，不许静默跳过。

---

## 四、五条铁律（已写入本项目 `AGENTS.md`，项目级生效）

| # | 铁律 |
|---|---|
| 1 | 任何代码修改前，先读 `fixlog/ARCHITECTURE.md` 与 `fixlog/API.md`；修改后同步更新受影响条目。 |
| 2 | 任何修复必须同时登记到 `fixlog/缺陷修复记录.md`，**未登记视为未完成**。 |
| 3 | 文档与代码不符时**以代码为准并立即修正文档**，不允许两种说法并存。 |
| 4 | 每次审核后的修复以该次审核结果为准；**上一批未修条目结转**继续跟踪。 |
| 5 | 本规则对项目在此对话框及新建对话框中的全部会话均生效，无需重复确认。 |

---

## 五、验收标准（交付前逐条自测）

- [ ] `fixlog/` 下存在 `ARCHITECTURE.md`、`API.md`、`缺陷修复记录.md`
- [ ] 架构文档能回答「某功能在哪个模块」（有功能索引表）
- [ ] 接口文档能回答「某接口入参与错误码」（有全局约定 + 错误码说明）
- [ ] 每批审核的清单条目数 = 该批记录条目数，且每条有终态
- [ ] 铁律已写入 `AGENTS.md`，新会话可读到

---

## 六、执行要点

**写文档时**：必须读源码取证，不许凭记忆或凭旧文档转写；关键事实标 `文件:行号`；
文首标「最后核对：YYYY-MM-DD（基于实际代码核验）」。

**收到审核意见时**：

```
① 整理成编号清单 → 写进台账「本批清单」（没清单不动手）
② 逐条修 → 每修完一条立刻改状态
③ 修不动的写「不修 + 理由」→ 进结转池
```

**禁止**：先改代码后补文档 · 改一堆再一次性补台账 · 有问题静默跳过 · 上一批未修条目凭空消失。

---

## 七、与其它纪律的关系

- 台账「验证方式」一列必须写**可复跑的命令或判据**，不接受「跑过了」。
- 若项目另有跨项目决策台账，本台账只管本项目代码层修复，不重复登记跨项目决策。
